# Test cases: Account registration

| ID | Title | Type | Linked scenario | Preconditions | Steps | Test data | Expected result | Priority |
|----|-------|------|-----------------|---------------|-------|-----------|-----------------|----------|
| TC-01 | New email registers a User account | Happy path | registering with a new email creates a User account | No account for the email | 1. `POST /register`<br>2. Inspect created account's role | `new@example.com` / `Str0ng-Passw0rd!` | Account created, role `User`, verification email sent | P1 |
| TC-02 | Case-insensitive duplicate is rejected without confirming existence | Negative | email uniqueness is case-insensitive | Account exists for `taken@example.com` | 1. `POST /register` with `Taken@Example.com` | `Taken@Example.com` | Treated as duplicate; response identical to TC-13's neutral response | P1 |
| TC-03 | Password under 10 characters is rejected | Negative | password below the minimum length is rejected | — | 1. `POST /register` with an 8-char password | `short12` | Validation error naming the length rule; no account created | P2 |
| TC-04 | Breached password triggers reject-or-warn | Negative | a breached password is rejected or flagged | HIBP corpus reachable | 1. `POST /register` with a known-breached password | e.g. `password123` | Either rejected, or account creation proceeds only after an explicit warning is shown | P2 |
| TC-05 | HIBP service unreachable does not silently bypass the check | Edge | (dependency note, story.md) | HIBP endpoint stubbed to fail | 1. `POST /register` with any password while the check is down | — | Behavior is a defined fallback (fail open with a logged warning, or fail closed) — not an unhandled exception | P2 |
| TC-06 | Injected role field is ignored | Negative | an injected role field is ignored on registration | — | 1. `POST /register` with `"role": "SystemAdmin"` in the payload | Valid email/password + role field | Account created with role `User`; SystemAdmin never granted | P1 |
| TC-07 | First Google login auto-creates an account | Happy path | first Google login auto-creates an account | No account tied to the Google identity | 1. Complete Google OAuth consent<br>2. Inspect resulting account | Google test account | `User` account created from verified OAuth email | P1 |
| TC-08 | OAuth with an existing local email requires proof of control | Edge | OAuth login matching an existing local account requires proof of control | Local account exists for the email | 1. | TC-09 | Unverified account can read but not write | Negative | unverified account is read-only on its own data | Registered, not verified | 1. Log in<br>2. `GET` own data<br>3. Attempt to log a meal | Unverified account | Read succeeds; write rejected with a clear "verify your email" message | P1 |
| TC-10 | Verification token older than 24h is rejected | Negative | verification token expires after 24 hours | Token issued >24h ago | 1. Visit verification link | Expired token | Rejected as expired; a path to request a new one is offered | P2 |
| TC-11 | Verification token cannot be reused | Negative | verification token is single-use | Token already consumed once | 1. Visit the same verification link again | Used token | Rejected as already used; account remains verified | P2 |
| TC-12 | Password reset completes and invalidates all sessions | Happy path | password reset completes and logs out every session | Valid unused reset token; ≥1 active session elsewhere | 1. `POST /password-reset/confirm` with new password<br>2. Attempt to use the old session elsewhere | Valid 1h token | Password updated; all prior sessions invalidated; token cannot be reused | P1 |
| TC-13 | Expired/used reset token is rejected without side effects | Negative | expired or already-used reset token is rejected | Token >1h old or already used | 1. `POST /password-reset/confirm` with that token | Expired/used token | Rejected; password unchanged; no sessions invalidated | P1 |
| TC-14 | Registering a taken email gives a neutral success-shaped response | Negative | registration response does not confirm an email is already registered | Account exists for the email | 1. `POST /register` with that email | `taken@example.com` | Response shape/wording matches a successful registration; no enumeration signal | P1 |
| TC-15 | Reset request for a nonexistent email is indistinguishable from a real one | Negative | password-reset request does not confirm whether the email exists | No account for the email | 1. `POST /password-reset/request` | `nobody@example.com` | Response identical to a real address's; no email actually sent | P1 |
| TC-16 | Registration and login enumeration responses match | Regression | (SRS FR-08, cross-story with auth-login) | Account exists for one test email, not the other | 1. Compare `POST /register` response for a taken email against `POST /login` response for a wrong password on a nonexistent email | `taken@example.com`, `nobody@example.com` | Neither endpoint's response, status, or timing lets an observer distinguish existing vs non-existing accounts | P2 |
